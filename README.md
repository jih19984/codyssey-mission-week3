# Mini NPU Simulator

## 프로젝트 개요

AI(CNN 등)가 이미지를 인식할 때 사용하는 MAC(Multiply-Accumulate, 곱하고-누적해서-더하기) 연산의 핵심 원리를
콘솔 프로그램으로 직접 구현한 미니 NPU 시뮬레이터다. 입력 패턴과 필터(십자가/X)를 위치별로 곱한 뒤 모두
더해 유사도 점수를 구하고, 점수가 더 높은 필터를 판정 결과로 출력한다. 3×3부터 25×25까지 크기를 늘려가며
연산 시간을 직접 측정해, 크기가 커질수록 연산량이 왜 O(N²)로 증가하는지 체감하는 것이 이 과제의 목표다.

## 실행 방법

```bash
python3 main.py
```

- 실행하면 `1) 사용자 입력(3x3)` / `2) data.json 분석` 중 모드를 선택한다.
- `data.json`은 `main.py`와 같은 위치(프로젝트 루트)에 있어야 한다.
- Python 3.8 이상, 외부 라이브러리 없이 표준 라이브러리(`json`, `time`)만 사용한다.

## 구현 요약

- **라벨 정규화 방식**: `data_loader.py`의 `LABEL_MAP` 딕셔너리(`{"+": "Cross", "cross": "Cross", "x": "X"}`)를
  이용해 `expected` 값과 필터 키에 등장하는 다양한 표기를 표준 라벨 `Cross`/`X` 두 가지로 통일한다.
  `normalize_label()`은 대소문자 차이도 흡수하도록 `.lower()`를 거친 뒤 조회하며, 정의되지 않은 값이 들어오면
  `KeyError`로 죽는 대신 `dict.get()`을 사용해 `None`을 반환하도록 했다(프로그램이 죽지 않아야 한다는 요구사항).
- **MAC 연산 구현 개요**: `mac_engine.compute_score(pattern, filter_)`는 `pattern.n × pattern.n`을 이중 for문으로
  순회하며 `pattern.get(i, j) * filter_.get(i, j)`를 누적합(accumulate)한다. NumPy 등 외부 라이브러리는 쓰지
  않았다. `[보너스]`로 `compute_score_flat()`도 추가했는데, `Matrix.flatten()`으로 1차원 리스트로 바꾼 뒤
  단일 for문으로 같은 연산을 수행한다(자세한 성능 비교는 아래 보너스 섹션 참고).
- **동점 처리 정책(epsilon)**: `mac_engine.judge()`는 두 점수를 `==`로 비교하지 않고
  `abs(score_a - score_b) < EPSILON`(`EPSILON = 1e-9`)로 비교한다. 부동소수점 연산은 `0.1 + 0.2 != 0.3`처럼
  이론상 같은 값도 미세한 오차로 다르게 나올 수 있기 때문에, 정확히 같은지가 아니라 "사실상 같은지"를 기준으로
  판정해야 한다(자세한 배경은 `docs/concepts/floating_point.md` 참고). 동점(또는 오차 범위 내)이면 `"UNDECIDED"`를
  반환한다.

## 결과 리포트

`python3 main.py` 실행 후 `2`(data.json 분석)를 선택했을 때의 실제 결과다.

### FAIL 케이스 원인 분석

`data.json`에는 의도적으로 서로 다른 원인의 FAIL 케이스 2개를 심어뒀고, 실제 실행 결과도 정확히 그 2개만 FAIL이었다.

1. **`size_13_3` — 비교 정책(동점/UNDECIDED) 문제**: 입력이 13×13 전부 1로 채운 행렬이다. `compute_score`는
   입력이 전부 1이면 사실상 "필터에서 1인 칸의 개수"를 세는 것과 같아지는데, Cross/X 필터 둘 다 1의 개수가
   `2×13-1=25`개로 정확히 같다. 그래서 `Cross 점수: 25`, `X 점수: 25`로 **정확히 동점**이 나오고,
   `judge()`가 `abs(25-25) < 1e-9`를 만족해 `"UNDECIDED"`를 반환한다. `expected`는 `"x"`(→`X`)였는데 판정이
   `UNDECIDED`라 둘이 달라서 FAIL 처리됐다. 이건 데이터나 로직의 버그가 아니라, "동점을 어떻게 처리할지"에
   대한 **의도된 정책 결과**다 — 만약 동점일 때 임의로 한쪽을 골랐다면 오히려 잘못된 확신을 주는 판정이 됐을 것이다.
2. **`size_25_3` — 데이터/스키마 문제**: 패턴 키는 `size_25_3`이라 `25×25` 필터와 비교돼야 하는데, 실제
   `input` 배열은 `24×24`로 저장돼 있다. `data_loader.iter_pattern_cases()`가 이 크기 불일치를
   `input_matrix`를 만들기 전에 미리 검증해서, MAC 연산을 아예 시도하지 않고 `"크기 불일치: 키는 25x25인데
   input은 24x24"`라는 사유와 함께 케이스 단위 FAIL로 처리했다. 예외가 터져서 프로그램이 죽는 대신, 이 케이스만
   건너뛰고 나머지 7개 케이스는 정상적으로 계속 처리된 것을 확인했다.

나머지 6개 케이스(`size_5_1/2`, `size_13_1/2`, `size_25_1/2`)는 모두 십자가 패턴을 Cross 필터에, X 패턴을 X
필터에 정확히 매칭시킨 경우라 판정과 `expected`가 일치해 PASS였다. 즉 이번 실행에서 FAIL이 0개가 아니라 2개
나온 건 데이터를 일부러 그렇게 설계했기 때문이고, 라벨 정규화(`+`/`cross`/`x` → `Cross`/`X`)와 epsilon 비교
정책이 없었다면 오히려 `size_13_3` 같은 케이스에서 부동소수점 오차나 표기 차이로 더 예측 불가능한 결과가
나왔을 것이다.

### 성능 표 해석 및 시간 복잡도(O(N²))

```
크기       평균 시간(ms)    연산 횟수
-------------------------------------
3×3            0.002           9
5×5            0.006           25
13×13          0.034           169
25×25          0.119           625
```

MAC 연산은 `n×n` 행렬의 모든 칸을 한 번씩 곱하고 더하므로, 연산 횟수는 정확히 `n²`이다(위 표의 "연산 횟수"
열이 `3²=9`, `5²=25`, `13²=169`, `25²=625`로 이론값과 그대로 일치한다). 측정된 평균 시간도 이 비율을 따라간다:
`13×13`은 `5×5`보다 연산 횟수가 `169/25 ≈ 6.8배`인데 측정 시간도 `0.034/0.006 ≈ 5.7배`로 비슷한 배율로
늘었고, `25×25`는 `13×13`보다 연산 횟수가 `625/169 ≈ 3.7배`인데 시간도 `0.119/0.034 ≈ 3.5배`로 거의 정확히
비례한다(가장 작은 `3×3`→`5×5` 구간은 절대 시간이 너무 작아 파이썬 함수 호출 자체의 고정 오버헤드 비중이
커서 비율이 덜 정확하다). 이처럼 "크기가 k배 늘면 시간도 k²배 가까이 늘어난다"는 관찰이 곧 MAC 연산이
O(N²) 시간 복잡도를 가진다는 근거다 — 이중 for문으로 `n`개의 행과 `n`개의 열을 전부 순회하니 당연한
결과지만, 직접 재서 눈으로 확인했다는 점이 이 과제의 핵심이었다.

## 보너스 구현

### 1. 패턴 생성기 (`pattern_generator.py`)

`generate_cross(n)`/`generate_x(n)`은 규칙(중앙 행/열 → Cross, 두 대각선 → X)만으로 N×N 패턴을 생성한다.
`data.json`의 실제 `size_5/13/25` 필터와 완전히 동일한 값을 만들어내는 것을 확인했다:

```
size=5:  cross 일치=True, x 일치=True
size=13: cross 일치=True, x 일치=True
size=25: cross 일치=True, x 일치=True
```

### 2. 1차원 배열 최적화 비교 (`mac_engine.compute_score_flat`)

`Matrix.flatten()`으로 2차원 리스트를 1차원(길이 N²)으로 바꾼 뒤 단일 for문으로 MAC 연산을 하도록
`compute_score_flat()`을 추가하고, 기존 `compute_score()`(2차원, 이중 for문)와 성능을 비교했다.

**① 매 호출마다 flatten을 포함해서 측정(공정하지 않은 비교)**

```
크기      2D 방식(ms)       1D 방식(ms)
----------------------------------------
3x3     0.0019          0.0027
5x5     0.0044          0.0061
13x13   0.0254          0.0345
25x25   0.0896          0.1191
```

이 결과만 보면 1D 방식이 오히려 더 느리다. `compute_score_flat()`이 호출될 때마다 `flatten()`으로 O(N²)
변환을 새로 수행하기 때문에, 실질적으로 "변환 O(N²) + MAC O(N²)"를 매번 반복해서 손해를 보는 것이다.

**② flatten을 미리 한 번만 해두고, 순수 MAC 루프만 측정(공정한 비교)**

```
크기      2D 루프(ms)       1D 루프(ms, 미리 flatten)
--------------------------------------------
3x3     0.0027          0.0008
5x5     0.0063          0.0015
13x13   0.0347          0.0073
25x25   0.1193          0.0274
```

변환 비용을 빼고 순수 MAC 루프만 비교하면 1차원 방식이 **약 3.5~4.7배 더 빠르다.** 이는 2D 방식이 매 위치마다
`get(i, j)`라는 메서드 호출(+ 내부적으로 `self.rows[i][j]` 이중 인덱싱)을 하는 반면, 1D 방식은 이미
평탄화된 리스트를 `flat[idx]`로 한 번만 인덱싱하기 때문이다. 즉 파이썬 리스트 자체는 어차피 포인터 배열이라
"메모리가 연속적이라 캐시에 유리하다"는 C 언어 수준의 이유보다는, **함수 호출/이중 인덱싱 오버헤드가
줄어든 것**이 실제 속도 차이의 주된 원인으로 보인다. 결론적으로 최적화 효과를 보려면 변환 비용을 매 호출마다
지불하지 않도록(예: 패턴/필터를 한 번만 flatten해서 재사용) 설계해야 한다는 것을 확인할 수 있었다.
